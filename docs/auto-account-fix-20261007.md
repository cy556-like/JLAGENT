# Auto 模式与账号模型选择修复

基线：`3af1d9551f5144182d344b63c48dd8be01728be4`。

## 已确认的代码问题

- 旧认证错误处理设置了全局“主 Key 失效”标记并提示已切换，但 Auto 对应的 GLM/Ark 客户端分支仍选原 Key，备用配置没有实际生效。
- `/models/set` 修改进程级默认模型，账号之间互相影响；多 worker 也不会同步这个内存状态。聊天请求本身不带模型选择。
- 旧认证判定包含泛化的“令牌”关键词，可能把其他错误误报成 Key 失效。

这能复现截图中的错误循环，但不能仅凭截图确认服务器上账号差异的唯一原因；服务器 Key 是否有效需要实际服务日志或部署后验证。

## 修复边界

- 已认证账号的选择单独保存在 `DATA_DIR/model_preferences/<账号SHA256>.json`。原子保存、跨 worker 读取；不保存密钥，不产生备份。Windows 短暂文件竞争最多重试 70ms，正常路径不等待。
- 模型列表、模型切换需要有效 JWT。新聊天、重试、文件上传显式携带 `model_id`；旧客户端缺省时读取该账号选择，没有保存则采用服务器默认值。
- 核心聊天和工具调用图绑定请求选择，包括网络重试重建。图缓存区分 Auto 和显式模型，避免另一个账号修改选择影响正在执行的调用。
- 保留 Auto→GLM-5.2、现有兜底顺序和 V4.1 峰时静默切换。所有普通候选因认证/额度错误失败后，才尝试已配置的不同备用 Key+地址；备用接口必须支持该模型和工具协议，缺少配置不会尝试。
- 认证/额度兜底在同一请求中执行。超时、网络错误、普通 400 参数错误不触发路由层跨模型切换；有正文/工具调用流输出后不拼接另一个模型的回答。原有同模型网络重试策略不变。
- 全部候选仍认证失败时准确报错，不再声称“已切换成功，请重新提问”。不将未完成回答伪装为成功。
- 前端忽略旧账号/过时请求的模型加载、切换响应。更新脚本和 service worker 缓存版本，布局不变。

不修改 `.env`、用户角色/用户名、聊天记录、8D/FMEA 业务提示词、依赖版本或服务启动方式。正常成功的聊天仍只请求一个模型，没有新增探测 API 或聊天前文件读取。
