# JLAGENT：20 个独立账号的负载保护（低负载修正）

本次只改后端资源保护和阻塞调用，不改模型、生成超时、备用切换、账号权限、前端布局、APK或依赖版本。无需重新安装依赖，部署代码后需要重启后端。不会自动备份文件。

## 默认保护

| 项目 | 默认值 | 满载行为 |
| --- | --- | --- |
| 全站聊天（含普通、流式、带文件聊天） | 20 | 新请求返回 503；不强停已经开始的聊天 |
| 单账号聊天 | 2 | 新请求返回 429；其他账号仍有各自名额 |
| 全站文件请求 | 20 | 新请求返回 503；与普通聊天的名额分开 |
| 单账号文件请求 | 4 | 新请求返回 429 |
| 文档处理 / 索引 | 10 | 在线程派发前异步排队，不占聊天线程 |
| 文档读取/解析 | 10 | 独立线程池及名额 |
| Word/Excel 导出 | 10 | 独立线程池及名额 |
| 每个 worker 的文档等待队列 | 64 | 排队满时明确返回错误，不自动重试付费调用 |
| 每条 SSE 的排队事件数 | 64 | 缓冲满后背压，不截断回答 |
| 系统可用内存下限 | 512 MB | 拒绝新的重请求；登录、历史、静态文件、下载及基础健康检查可访问 |

普通内存状态下，10 个不同文件任务可以同时开始，没有按在线人数延迟，也没有无竞争时的固定等待。CPU 密集型转换仍受实际核数/GIL影响，模型供应商的限速也没有改变。可用内存低于 1536 MB 时，对新工作降低并发名额（按每 256 MB 余量估算，保留 512 MB），已开始的工作不被强停。这不是准确的每文件内存预估，不保证杜绝 OOM。

带文件聊天完成文件处理、开始发送响应头时释放文件请求名额，聊天名额保持到流结束。取消排队中的操作会将其移除；取消 HTTP 请求不能停止运行中的 Python 线程，该文件请求的名额保留到真实工作结束。模型流断开时显式关闭生成器并回收生产任务。

负载错误保持前端既有的 detail 格式及 Retry-After: 3，不自动重复发起模型调用。

## 并行与共享数据

文档处理、读取、导出使用独立线程池，不与默认聊天/检索线程池竞争。异步路由和 LangGraph 异步文档工具在线程派发前等待名额；工具保留原同步接口、参数定义及输出格式。

同知识库的不同文件可并行加载及向量化。只有写入向量批次、关键词 JSON 的读-改-写才互斥；远程 Embedding 等待不占这些写锁。关键词文件原子替换，不先清空旧文件；临时文件不是备份，写入后清理。保存并索引一个上传文件保持一个事务，避免旧失败任务误删新上传。同文件的修改、索引、删除互斥；重建/删除整个知识库独占该知识库，不独占其他知识库。全库迁移是维护操作，与普通索引互斥。

向量客户端冷初始化复用现有进程内互斥，缓存命中不等待冷启动锁。阻塞的邻接切片读取和初始化仍在工作线程执行，原混合检索并行及结果融合不变。文件保存复用已经通过 50 MB 校验的读取结果。

## 多 worker 与后台索引

名额通过 DATA_DIR/runtime_resource_locks/*.lock 的操作系统文件锁共享。同机 worker 必须使用同一个 DATA_DIR；不支持跨主机共享名额。进程退出由操作系统释放锁，不使用 PID 猜测、心跳超时或数据库轮询。服务运行时不要删除锁文件。

每个 worker 的后台重索引最多 4 个线程、32 个待处理文件键。同文件重复修改合并为最新一次重索引；队列满时同步索引并返回真实结果，不丢弃修改。实际索引工作仍受全局文档名额控制。后台工作保留账号/会话上下文，但不继承前一请求的锁所有权。

## 可选配置

默认无需修改 .env。若以前手工设置了更小的值，环境变量仍优先，需要自行调整或移除。

```dotenv
JLAGENT_CHAT_CONCURRENCY=20
JLAGENT_USER_CHAT_CONCURRENCY=2
JLAGENT_FILE_CONCURRENCY=20
JLAGENT_USER_FILE_CONCURRENCY=4
JLAGENT_DOCUMENT_CONCURRENCY=10
JLAGENT_DOCUMENT_READ_CONCURRENCY=10
JLAGENT_EXPORT_CONCURRENCY=10
JLAGENT_DOCUMENT_PENDING_LIMIT=64
JLAGENT_SOFT_FREE_MEMORY_MB=1536
JLAGENT_SSE_BUFFER_EVENTS=64
JLAGENT_MIN_FREE_MEMORY_MB=512
```

GET /health 的 resource_limits 显示实际配置及有效文档名额，不冒充跨进程实时活跃人数。

```cmd
python -X utf8 -m unittest discover -s tests -p "test_resource*.py" -v

```

离线测试覆盖 10 文件请求同时准入、三个文档通道各 10 任务同时开始、无竞争时不延迟、等待者不占线程、默认聊天线程不被挤占、取消排队/运行任务的生命周期、队列上限、不同文件并行/同文件串行、知识库维护互斥、独立账号同名文件、关键词并发更新无丢失、写入失败保持旧索引、向量调用次数/元数据/ID、后台锁所有权、真实 LangChain 同步及异步工具兼容，以及原有 20 账号/模型路由/SSE 回归。

这是离线资源控制验证，不是服务器上 20 人调用真实模型的压测。2.5 GHz 未说明 CPU 核数；8 GB 是否充足仍取决于知识库、文件体积、worker 数、其他服务和模型供应商配额。多 worker 复制缓存，不能靠增加 worker 保证速度。内存保护是启发式准入，不保证运行中的任务不会继续增长内存。本次不属于整个项目的安全审计。
