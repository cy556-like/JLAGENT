# JLAGENT：20 个独立账号的负载保护

本次只改后端资源保护和阻塞调用，不改模型、生成超时、备用切换、账号权限、前端布局、APK或依赖版本。无需重新安装依赖，部署代码后需要重启后端。不会自动备份文件。

## 默认保护

| 项目 | 默认值 | 满载行为 |
| --- | --- | --- |
| 全站聊天请求（含普通、流式、带文件聊天） | 20 | 新请求返回 503；不强停已经开始的聊天 |
| 单账号聊天请求 | 2 | 新请求返回 429；其他账号仍有各自名额 |
| 全站文件请求（上传、修改、重建、导出等） | 2 | 新请求返回 503；不占用普通聊天的文件名额 |
| 单账号文件请求 | 1 | 新请求返回 429 |
| 文档写入、索引重建、后台重索引 | 1 | 在线程里等待，不阻塞 ASGI 事件循环 |
| 文档读取/解析 | 2 | 使用独立名额，不必等云端建索引结束 |
| Word/Excel 导出 | 1 | 使用独立名额，不必等建索引结束 |
| 每条 SSE 的排队事件数 | 64 | 缓冲满后施加背压，不截断回答 |
| 系统可用内存下限 | 512 MB | 拒绝新的重请求；登录、历史、静态文件、下载及基础健康检查仍可访问 |

带文件聊天在完成文件处理、开始发送响应头时释放文件请求名额，聊天名额保持到流结束。取消 HTTP 请求不能停止已经运行的 Python 线程：该文件请求的名额会保留到实际工作结束，避免反复取消导致后台过量堆积。模型流断开时显式关闭生成器并回收生产任务。

负载错误仍返回前端既有的 `detail` 格式和 `Retry-After: 3`，不自动重试或重复发起付费模型调用。

## 多 worker 与后台索引

名额通过 `DATA_DIR/runtime_resource_locks/*.lock` 的操作系统文件锁共享；同一台机器的 worker 必须使用同一个 DATA_DIR。进程退出/崩溃由操作系统释放锁，不使用 PID 猜测、心跳超时或轮询数据库。服务运行时不要删除这些锁文件，不支持跨主机分布式名额。

每个 worker 的后台重索引最多 1 个线程、32 个待处理文件键；同文件的重复修改合并为最新一次重索引。队列满时在已准入的工作线程同步索引，并返回真实成功/失败结果，不丢弃修改。所有 worker 的实际索引工作仍受到上述全局名额控制。

向量库冷启动使用进程内互斥，避免同一 collection 的同时首次访问重复初始化；已有缓存不等待冷启动锁。异步检索的冷启动和相邻切片读取移到工作线程，保留原来的查询并行、结果融合和切片语义。文件保存复用经过 50 MB 校验的读取结果，并放入线程，避免慢磁盘卡住其他聊天。

## 可选配置

不需要改 .env，默认值已经生效。确需调整时可以使用：

```dotenv
JLAGENT_CHAT_CONCURRENCY=20
JLAGENT_USER_CHAT_CONCURRENCY=2
JLAGENT_FILE_CONCURRENCY=2
JLAGENT_DOCUMENT_CONCURRENCY=1
JLAGENT_DOCUMENT_READ_CONCURRENCY=2
JLAGENT_EXPORT_CONCURRENCY=1
JLAGENT_SSE_BUFFER_EVENTS=64
JLAGENT_MIN_FREE_MEMORY_MB=512
```

`GET /health` 的 `resource_limits` 会显示实际限额和当前可用内存，不冒充跨进程实时活跃计数。

## 验证与边界

离线测试覆盖 20 账号并发准入、单账号配额、真实跨进程锁与进程退出释放、文件与聊天名额独立、慢消费者背压、完整输出顺序、断开/异常清理、取消后的真实线程生命周期、索引队列上限及合并、缓存冷启动复用、阻塞操作线程化和既有账户模型路由。

```cmd
python -X utf8 -m unittest discover -s tests -p test_resource_guard.py -v
python -X utf8 -m unittest discover -s tests -p test_auto_account_routing.py -v
```

这是离线准入与生命周期验证，不是服务器上 20 人调用真实模型的性能压测。2.5 GHz 未说明 CPU 核数；8 GB 是否充足仍取决于 worker 数量、知识库体积、图片/文件大小、其他服务以及模型供应商限额。多 worker 会复制缓存，不能通过增加 worker 数量保证性能。内存保护在新请求准入时检查，不保证已经准入的任务不会继续增长内存。未改动既有认证/权限，也不将本次优化视为整个项目的安全审计。
